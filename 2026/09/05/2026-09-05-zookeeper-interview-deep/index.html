Q1. Zookeeper 是什么？解决什么问题？

一句话定位：ZooKeeper 是 Apache 开源的分布式协调服务，专门解决分布式系统中的一致性协调难题。

背景故事：分布式系统最头疼的问题不是性能，而是”协调”——多台机器同时干活，怎么保证大家步调一致？比如：

  • 多个节点同时抢同一把锁，谁抢到算谁的？
  • 集群里哪台机器是 Master，大家怎么达成共识？
  • 配置文件改了，怎么通知所有节点及时更新？

这些问题每个系统都要解决，与其各自造轮子，不如交给 ZooKeeper 统一处理。

ZooKeeper 能做什么：

能力 典型使用场景
分布式锁 多节点抢占同一资源
Master 选举 Kafka Controller 选举、HBase Master
服务注册发现 早期 Dubbo 注册中心
配置中心 配置热更新
分布式屏障 多节点同步等待
命名服务 全局唯一 ID 生成

核心设计哲学：ZooKeeper 并不自己实现这些功能，而是提供一套原语（树形数据模型 + Watch 机制 + Session 管理），让开发者在这些原语上组合出各种协调逻辑。就像乐高积木，基础块很简单，但能拼出各种复杂形状。

ZooKeeper 的保证：

  1. 顺序一致性：同一客户端的操作按提交顺序执行
  2. 原子性：每个操作要么成功要么失败，没有中间状态
  3. 单一系统映像：客户端看到的视图是一致的
  4. 可靠性：一旦写入成功，数据不丢失
  5. 实时性：客户端会在有限时间内看到最新数据（有界滞后）

Q2. ZNode 的4种类型

ZNode 是 ZooKeeper 数据模型的基本单元，类似文件系统中的”文件+目录”的混合体。ZNode 有 4 种类型，理解它们是理解一切 ZK 应用的基础。

逐类详解：

1. 持久节点（PERSISTENT）

最普通的节点，创建后一直存在，直到你主动删除它。适合存储配置信息、命名空间定义等需要长期保留的数据。

2. 临时节点（EPHEMERAL）

Session 断开后自动删除，是实现服务注册发现和分布式锁的核心原语。重要限制：临时节点不能有子节点（因为 Session 断开时 ZK 无法保证原子地删除整棵子树）。

3. 持久顺序节点（PERSISTENT_SEQUENTIAL）

创建时 ZK 自动在节点名后追加一个全局单调递增的 10 位数字序号（如 /lock/node-0000000001）。适合实现需要记录操作顺序的场景。

4. 临时顺序节点（EPHEMERAL_SEQUENTIAL）

最常用的高级类型！同时具备”Session 断开自动删除”和”顺序编号”两个特性。分布式公平锁就是靠它实现的（详见 Q12）。

类型 Session 断开删除 顺序编号 能有子节点
PERSISTENT 否 否 是
EPHEMERAL 是 否 否
PERSISTENT_SEQUENTIAL 否 是 是
EPHEMERAL_SEQUENTIAL 是 是 否

Q4. Watch 机制：一次性触发、事件类型、持续监听

Watch 机制是 ZooKeeper 最核心的特性之一，它让客户端能够监听节点变化并异步接收通知。

一次性触发原理：

Watch 是一次性的。每次 Watch 触发后自动失效，如果想继续监听，必须重新注册 Watch。这个设计是为了减少 ZK 服务端的内存开销——如果 Watch 永久有效，服务端需要维护海量长连接订阅关系。

Watch 事件类型：

事件类型 触发条件
NodeCreated 监听的节点被创建
NodeDeleted 监听的节点被删除
NodeDataChanged 节点数据发生变化
NodeChildrenChanged 子节点列表发生变化（增加或删除子节点）

不同 API 注册的 Watch 监听不同事件：

  • getData(path, watch) → 监听 NodeDeleted、NodeDataChanged
  • exists(path, watch) → 监听 NodeCreated、NodeDeleted、NodeDataChanged
  • getChildren(path, watch) → 监听 NodeDeleted（父节点删除）、NodeChildrenChanged

Watch 的注意事项：

  1. Watch 通知是异步的，客户端收到通知时数据可能已经被修改多次
  2. Watch 通知不携带变化后的数据，需要重新调用 getData 获取
  3. 网络断开重连后，之前注册的 Watch 会丢失，需要应用层重新注册

Q6. ZAB 协议（Zookeeper Atomic Broadcast）

ZAB 是 ZooKeeper 的核心一致性协议，全称 ZooKeeper Atomic Broadcast（ZooKeeper 原子广播协议）。它保证了 ZK 集群的数据一致性和高可用性。

ZAB 协议分为两个阶段：崩溃恢复和消息广播。

阶段一：崩溃恢复（Leader 选举）

当集群启动或 Leader 宕机时，触发崩溃恢复，通过选举选出新 Leader（详见 Q7）。

阶段二：消息广播（正常工作阶段）

一旦有了 Leader，就进入消息广播阶段，所有写请求都通过 Leader 处理：

关键特性：两阶段提交 + 过半写成功

Leader 发出 Proposal 后，只需要收到过半节点（包含自身）的 ACK，就可以发出 Commit，不需要等所有节点确认。这是 ZK 在一致性和可用性之间的权衡——牺牲了强一致性（少数节点可能滞后），换来了高可用性。

ZAB 的数据恢复保证：

崩溃恢复阶段，ZAB 必须满足两个条件：

  1. 已提交的事务必须恢复：如果事务已在 Leader 上 Commit 并发给了 Follower，选出新 Leader 后这条事务不能丢
  2. 未提交的事务必须丢弃：如果 Leader 只是 Propose 了事务但还没 Commit 就宕机了，新 Leader 必须丢弃这条事务

这就是 ZXID 中 epoch 字段的作用——新 Leader 的 epoch 比旧 Leader 大，旧 epoch 的未提交事务会被自动丢弃。

Q7. Leader 选举流程（FastLeaderElection）

ZooKeeper 默认使用 FastLeaderElection（快速 Leader 选举） 算法，依赖三个核心参数：

  • myid：每台机器的唯一标识，配置在 myid 文件中（整数，通常 1~255）
  • ZXID：最新事务 ID，ZXID 越大说明数据越新
  • epoch：选举轮次，每次选举 epoch 加 1

选举规则（谁能当 Leader）：

优先选 epoch 最大的 → epoch 相同选 ZXID 最大的 → ZXID 相同选 myid 最大的

选举期间集群不可用：选举过程中，集群不处理任何读写请求。典型的选举时间是 200ms ~ 几秒，取决于网络状况和节点数量。

Leader 宕机后的重新选举：Follower 检测到与 Leader 的连接断开（超过一定时间收不到心跳），立刻进入 LOOKING 状态，触发新一轮选举，epoch 自动加 1，旧 Leader 的未提交事务被丢弃。

Q8. Leader、Follower、Observer 三种角色

Leader：

  • 集群唯一的写入节点，所有写请求必须经过 Leader
  • 负责发起事务 Proposal，收到过半 ACK 后 Commit
  • 维护与所有 Follower/Observer 的心跳连接
  • 参与 Leader 选举投票

Follower：

  • 处理客户端读请求（本地直接返回）
  • 转发写请求给 Leader
  • 接收 Leader 的 Proposal 并 ACK，接收 Commit 后提交到本地
  • 参与 Leader 选举投票（这是与 Observer 最大的区别）

Observer：

  • 职责与 Follower 基本相同（处理读、转发写、同步数据）
  • 不参与 Leader 选举投票
  • 不参与写事务的 Quorum（不需要给 Proposal 发 ACK）

为什么需要 Observer：

假设你想扩大集群规模提升读性能，直接加 Follower 会有问题：Follower 越多，Leader 等待 ACK 的时间越长，写性能下降。Observer 的引入解决了这个矛盾——加 Observer 可以提升读性能，又不影响写性能。

Q9. ZXID 的结构：高32位（epoch）+ 低32位（事务计数）

ZXID（ZooKeeper Transaction ID，事务ID）是一个 64 位长整数，结构如下：

epoch（高32位）：

每次 Leader 选举成功，epoch 加 1。新 Leader 上任后，所有事务的 ZXID 中 epoch 部分都会更新为新值。这确保了：

  • 新 Leader 的事务 ZXID 一定大于旧 Leader 的所有事务 ZXID
  • 旧 Leader 生成的未提交事务（带旧 epoch）在新 Leader 上会被识别并丢弃

counter（低32位）：

同一任 Leader 内，每产生一条事务，counter 加 1，严格单调递增。这保证了同一任 Leader 期间，事务有全局顺序。

ZXID 的作用：

在选举中的作用：ZXID 越大说明节点见过的事务越多，数据越新，优先当 Leader，避免数据回滚。

Q10. Zookeeper 的一致性保证：顺序一致性，读到旧数据的场景

这是面试高频考点，很多人以为 ZK 是强一致性，其实不然。

ZooKeeper 提供的是顺序一致性（Sequential Consistency），不是强一致性（Linearizability）。

区别：

  • 强一致性：写入完成后，任意节点立刻能读到最新值
  • 顺序一致性：同一客户端的操作有序，但不同客户端可能读到旧值

为什么会读到旧数据：

Follower 接收到 Commit 是异步的，Leader commit 后 Follower 可能有几毫秒到几十毫秒的延迟才能同步到。

如何强制读到最新数据（sync 操作）：

sync() 的原理：客户端发送一个 sync 请求给连接的 Follower，Follower 将这个请求转发给 Leader，Leader 处理后告知 Follower 已同步到最新，然后客户端再发 getData 请求。

ZK 适合做什么：

由于存在读旧数据的可能性，ZK 不适合做要求强一致读的场景。ZK 的典型应用（分布式锁、选举、配置中心）都能容忍短暂的不一致，因为 Watch 机制会在数据变化后及时通知。

Q13. 分布式锁 vs Redis 分布式锁

这是常见对比题，考察你对两种方案权衡的理解。

ZooKeeper 分布式锁：

优点：

  • 天然公平锁：顺序节点保证先来先得，不会饥饿
  • 自动释放：客户端宕机后，临时节点自动删除，锁自动释放，不存在死锁风险
  • Watch 机制高效：等待者不需要轮询，Watch 触发即唤醒
  • 强一致性保证：ZAB 协议确保锁操作的原子性

缺点：

  • 性能较低：每次加锁都需要创建 ZNode，涉及一次或多次写操作，需要 Leader 广播，RT 较高（通常 5~20ms）
  • ZK 集群本身的稳定性：选举期间不可用

Redis 分布式锁：

优点：

  • 极高性能：单节点 Redis 内存操作，QPS 轻松 10w+，延迟 < 1ms
  • 简单易用：SET key value NX PX timeout 一条命令搞定

缺点：

  • 非公平锁：多个客户端竞争时，谁先请求 Redis 就谁得到锁，不保证先来先得
  • 锁超时问题：业务执行时间超过锁超时时间，锁自动释放，可能出现两个客户端同时持有锁
  • 主从切换风险（Redlock 问题）：Redis 主从异步复制，主节点宕机后从节点可能没同步到锁，新主节点上锁丢失

选型建议：

场景 推荐方案
高并发、对延迟敏感、允许偶尔异常 Redis 分布式锁
对公平性要求高、不能有死锁风险 ZK 分布式锁
金融/支付等严格场景 ZK 或 Redlock（Redis 多节点方案）

Q18. Paxos vs ZAB：两者关系

这道题考察你对分布式一致性协议历史的理解。

Paxos 是什么：

Paxos 是 Leslie Lamport 在 1989 年提出的分布式一致性算法，被认为是分布式系统领域最重要的算法之一。它解决了如何在不可靠网络中的多台机器上对某个值达成共识的问题。

Paxos 的角色：

  • Proposer：提出提案
  • Acceptor：接受/拒绝提案
  • Learner：学习已达成共识的值

ZAB 与 Paxos 的关系：

ZAB 的设计者（Flavio Junqueira 等）明确表示 ZAB 借鉴了 Paxos 的思想，但专门为 ZooKeeper 的使用场景做了定制优化。

主要区别：

维度 Paxos ZAB
目的 通用分布式共识 专为 ZK 设计（Primary-Backup 模式）
操作单元 对单个值达成共识 对有序事务序列广播
顺序保证 不保证（需要 Multi-Paxos 扩展） 严格保证全局顺序
Leader 概念 Paxos 有 Primary 角色 Leader 是核心，所有写必须经过 Leader
崩溃恢复 通用处理 专门设计的崩溃恢复阶段

ZAB 的核心创新：

ZAB 相比 Paxos 多了一个核心设计——主备模式下的有序广播。ZK 的所有数据变更都是有序的，ZXID 严格单调递增，这在 Paxos 的通用框架里不是天然保证的。

简单说：Paxos 是通用算法，ZAB 是 Paxos 的特化版本，专门优化了 ZK 的主备复制和有序事务场景。

Q19. ZAB vs Raft：两种共识算法的对比

Raft 是 Diego Ongaro 在 2014 年提出的共识算法，目标是比 Paxos 更易于理解和实现。etcd、TiKV、CockroachDB 等都用了 Raft。

核心对比：

维度 ZAB（ZooKeeper） Raft（etcd/TiKV）
设计目标 专为 ZK Primary-Backup 设计 通用，易于理解
Leader 选举 FastLeaderElection（基于 ZXID + epoch + myid） 基于 Term + Log Index
日志复制 2PC 广播（Propose + Commit） AppendEntries RPC
成员变更 需手动配置，不支持动态 支持 JointConsensus 动态成员变更
工程实现 ZK 特有，难复用 易于移植，etcd/Raft 库可直接使用
读性能 Follower 可读（可能旧数据） 默认 Leader 读，可配置 Follower 读
生态 Kafka（已迁移）、Hadoop etcd、Consul、TiKV

选举机制的区别：

Raft 更易理解的原因：Raft 将共识问题分解为 Leader 选举、日志复制、安全性三个独立子问题，每个子问题有清晰的边界和规则，便于实现和验证。ZAB 的实现细节更多地与 ZK 的特定架构耦合。

结论：如果你要在系统中嵌入共识模块，优先选 Raft（有成熟库）；ZK/ZAB 作为现成的协调服务，不需要关心其内部算法实现。

Q20. ZK 的性能瓶颈

写操作必须经过 Leader：

所有写操作（create、setData、delete）都必须由 Leader 处理并广播，即使你的客户端连接到 Follower，Follower 也会将写请求转发给 Leader。这意味着：

  • 写操作的延迟 = 客户端到 Follower 的延迟 + Follower 到 Leader 的延迟 + Leader 广播到过半节点的延迟
  • Leader 是写操作的单点，Leader 的吞吐量上限就是集群的写吞吐量上限
  • 典型写 QPS：单集群 1000~5000 ops/s（视机器配置和网络情况）

读操作可能读到旧数据：

读操作由 Follower 本地直接返回，不经过 Leader，因此：

  • 读性能高（本地内存读取，延迟 < 1ms）
  • 但可能读到过期数据（Follower 未完全同步最新写入）

其他性能限制：

性能调优建议：

ZK 不适合的场景：

  • 大数据量存储（数据量应 < 内存大小）
  • 高频写入（写 QPS > 5000）
  • 强一致性读（需要加 sync）

Q22. ZK 客户端（Curator）：为什么用 Curator 而不是原生客户端

原生 ZooKeeper 客户端的痛点：

原生客户端存在的问题：

  1. 连接是异步的，需要手动等待连接建立
  2. 没有自动重试，网络抖动时请求失败需要自己处理
  3. Watch 是一次性的，持续监听需要手动重注册，代码复杂且容易漏
  4. 没有高级抽象，分布式锁、Leader 选举、服务发现都要从零实现
  5. Session 管理复杂，Session 过期后的恢复需要自己处理

Curator 的解决方案：

Curator 是 Netflix 开源的 ZooKeeper 客户端封装库，现已成为 Apache 项目。它解决了原生客户端的所有痛点：

Q24. ZK 在 Kafka 中的作用（已向 KRaft 迁移）

历史上，Kafka 重度依赖 ZooKeeper 来管理集群元数据。理解这段历史有助于理解 ZK 的典型使用场景。

ZK 在 Kafka 中承担的功能：

具体作用：

  1. Broker 注册：Broker 启动时在 /brokers/ids/ 下创建临时节点，宕机后自动删除
  2. Controller 选举：所有 Broker 争抢创建 /controller 临时节点，成功者为 Controller（负责 Partition Leader 选举）
  3. Topic 元数据管理：Topic 创建/删除/配置变更写入 ZK
  4. Consumer 组管理（旧版本）：Consumer Offset 存储在 ZK（新版本已迁移到 __consumer_offsets Topic）

KRaft 迁移（Kafka 2.8+ / 正式 GA 在 3.3+）：

Kafka 社区推进了 KRaft（Kafka Raft Metadata Mode） 项目，用内置的 Raft 共识协议替代 ZooKeeper，解决了以下问题：

  • ZK 成为外部依赖，增加了运维复杂度
  • ZK 的扩展性限制了 Kafka 的 Partition 数量上限
  • Controller 切换期间依赖 ZK 导致恢复时间较长

面试建议：提到 ZK 在 Kafka 的作用时，要同时提到 KRaft 迁移，显示你的知识是最新的。

Q25. 面试高频：ZK Leader 宕机，服务调用会受到什么影响？

这道题考察你对 ZK 可用性的深刻理解，是区分背八股文和真正理解的分水岭。

影响分析（不可用时间窗口）：

不同操作的影响程度：

写操作（100% 受影响）：

Leader 宕机后，所有写操作（create、setData、delete）都会失败，客户端收到 ConnectionLoss 或 SessionExpiredException。业务系统如果依赖 ZK 写操作（如服务注册、配置更新），这段时间会失败。

读操作（Follower 仍可提供）：

如果客户端连接的是 Follower，Follower 在选举期间仍然可以处理读请求（返回本地缓存数据，但可能是稍旧的数据）。

Watch 通知（可能延迟或丢失）：

选举期间，新的 Watch 事件通知可能延迟。如果 Watch 事件发生在选举期间，理论上可能丢失（ZK 不保证 100% 不丢通知，但实际极少丢失）。

服务调用的影响（以 Dubbo + ZK 注册中心为例）：

最佳实践（降低 ZK 不可用的影响）：

  1. 本地缓存：客户端框架（Dubbo、Spring Cloud ZK）应该将服务列表缓存到本地文件，ZK 不可用时从本地文件恢复
  2. 优雅降级：ZK 不可用期间，只影响注册/发现，不影响已建立的调用链路
  3. 奇数节点 + 异地容灾：3个机房各放 1~2 个 ZK 节点，避免单机房故障导致整个集群不可用
  4. 监控告警：监控 ZK 选举次数，选举频繁说明集群不稳定

一句话总结回答：Leader 宕机后，ZK 集群进入选举阶段，选举期间（通常 1~30 秒）所有写操作失败，读操作可能返回旧数据。对于已完成服务发现并有本地缓存的服务消费者，影响较小；对于正在注册或需要实时感知服务变更的场景，会有短暂不可用。这也是为什么生产环境推荐 ZK 集群 + 本地缓存兜底的组合方案。
