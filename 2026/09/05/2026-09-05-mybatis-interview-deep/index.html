Q1. MyBatis 是什么？和 Hibernate 的本质区别（半自动 vs 全自动 ORM）

MyBatis 是什么？

MyBatis 是一款优秀的持久层框架，它支持自定义 SQL、存储过程以及高级映射。MyBatis 免除了几乎所有的 JDBC 代码以及设置参数和获取结果集的工作，通过简单的 XML 或注解来配置和映射原始类型、接口和 Java POJO（Plain Old Java Objects，普通老式 Java 对象）为数据库中的记录。

半自动 vs 全自动 ORM：核心区别

对比维度 MyBatis（半自动） Hibernate（全自动）
SQL 控制权 开发者自己写 SQL 框架自动生成 SQL
学习成本 低，会 SQL 就能上手 高，HQL/Criteria/缓存策略
灵活性 极高，SQL 随心所欲 较低，复杂查询需绕道
数据库移植性 差（SQL 与数据库方言绑定） 好（HQL 屏蔽方言差异）
适用场景 互联网高并发、复杂业务查询 快速开发、CRUD 简单场景

一句话记忆：

  • MyBatis：我告诉你 SQL，你帮我执行并把结果映射成对象。
  • Hibernate：你告诉我对象关系，我来决定怎么查数据库。

国内互联网公司（阿里、美团、字节）几乎清一色选 MyBatis，原因就是 SQL 可控、性能可调、DBA 可以 review。

Q2. MyBatis 整体架构（SqlSessionFactory → SqlSession → Executor → StatementHandler → ResultSetHandler）

MyBatis 的架构分为三层，从上到下依次是：

各组件职责：

  • Configuration：全局配置对象，解析 mybatis-config.xml 和所有 Mapper XML，存储所有映射信息。
  • SqlSessionFactory：创建 SqlSession 的工厂，应用启动时创建一次，全局单例。
  • SqlSession：数据库会话，提供 CRUD 方法，内部持有 Executor。
  • Executor：真正执行 SQL 的地方，分三种：Simple（默认）、Reuse（复用 Statement）、Batch（批量）。
  • StatementHandler：对 JDBC PreparedStatement 的封装，负责 SQL 预编译和参数绑定。
  • ResultSetHandler：把 JDBC ResultSet 映射成 Java 对象，是 <resultMap> 发挥作用的地方。

插件的切入点正是这四个处理器接口：Executor、StatementHandler、ParameterHandler、ResultSetHandler。

Q4. SqlSession 的生命周期和线程安全问题（为什么不能是单例）

SqlSession 的生命周期：

标准用法（非 Spring 环境）：

为什么不能是单例？

SqlSession 内部持有：

  1. 数据库连接（Connection）：每个线程应该有独立的连接
  2. 一级缓存（Local Cache）：HashMap，线程 A 的缓存不能被线程 B 读到
  3. 未提交事务：事务状态不能在线程间共享

如果把 SqlSession 做成单例，多线程并发时会出现：

  • 数据库连接竞争
  • 脏读（线程 A 读到线程 B 还未提交的缓存）
  • 事务混乱

Spring 如何解决这个问题？

Spring 通过 SqlSessionTemplate 解决了线程安全问题。SqlSessionTemplate 内部使用 ThreadLocal 绑定 SqlSession，每个线程有自己独立的会话，用完自动关闭。这就是为什么在 Spring 项目里，@Autowired 注入的 Mapper 可以放心当单例使用。

答案：JDK 动态代理 + MapperProxy

绑定流程：

  1. 注册阶段：MyBatis 启动时，扫描到 UserMapper 接口，将其注册到 MapperRegistry，与对应的 XML namespace 绑定。

Namespace 必须与接口全限定名一致，就是这个原因。

Q7. MyBatis 执行一条 select 语句的完整流程（从 mapper.selectById() 到 JDBC）

面试官最爱问的流程题，把这个说清楚，至少 80 分。

关键节点说明：

  1. 一级缓存检查：在真正查数据库之前，先查本次 SqlSession 的缓存（一个 HashMap），key 是 statementId + 参数 + 分页范围 + SQL。

  2. SQL 预编译：StatementHandler.prepare() 调用 connection.prepareStatement(boundSql.getSql())，得到 PreparedStatement。

  3. 参数绑定：ParameterHandler.setParameters() 遍历参数，调用 TypeHandler 把 Java 类型转换成 JDBC 类型并设置到 PreparedStatement。

  4. 结果映射：ResultSetHandler 遍历 ResultSet，根据 <resultMap> 或字段名映射规则，用反射把每一行转成 Java 对象。

Q8. 一级缓存（SqlSession 级别）：原理、失效条件、坑点（Spring 集成后默认失效）

一级缓存的原理：

一级缓存是 SqlSession 级别的缓存，每个 SqlSession 内部有一个 PerpetualCache（本质是 HashMap）。同一个 SqlSession 执行相同的 SQL 且参数相同，第二次直接从 HashMap 读取，不再查数据库。

一级缓存的失效条件：

  1. SqlSession 关闭（缓存随之销毁）
  2. 调用了 session.clearCache()
  3. 执行了 INSERT / UPDATE / DELETE 操作（会清空整个 SqlSession 的缓存）
  4. <select> 标签配置了 flushCache="true"

最大的坑：Spring 集成后一级缓存几乎失效！

Spring 的事务管理下，每次 Mapper 方法调用都可能使用不同的 SqlSession（因为 SqlSessionTemplate 在没有事务的情况下，每次调用完就关闭 SqlSession）。

结论：不加 @Transactional 的情况下，MyBatis 一级缓存在 Spring 中基本不生效。

Q10. 为什么 MyBatis 默认关闭二级缓存？（脏读风险，多表关联场景）

虽然 cacheEnabled 默认是 true，但每个 Mapper XML 默认不声明 <cache>，所以实际上二级缓存默认不生效。原因如下：

原因一：脏读风险

二级缓存是 namespace 级别的。如果 UserMapper 开了二级缓存，但另一个 OrderMapper 修改了 user 表（比如在 order 中记录了用户姓名），UserMapper 的缓存不会失效，导致读到过期数据。

原因二：多表关联场景复杂

实际业务中，一条 SQL 可能 JOIN 了多张表，如果这几张表各自有不同的 Mapper，任何一个表变更都可能导致缓存失效，但 MyBatis 的二级缓存无法跨 namespace 联动失效。

最佳实践：

  • 生产环境不推荐使用 MyBatis 二级缓存
  • 需要缓存时，使用 Redis 等独立缓存方案，业务代码自行控制失效逻辑
  • 只在数据几乎不变、查询频繁的场景（如字典表、配置表）中谨慎使用

Q17. N+1 查询问题：产生原因及 fetchType=eager 的权衡

N+1 问题描述：

查询 1 个用户列表（1 条 SQL），再为每个用户查询其订单（N 条 SQL），共 N+1 条 SQL。

解决方案：

方案一：改为 fetchType="eager"

立即加载，一次 JOIN 查询搞定，但如果不需要订单数据，就做了无用的 JOIN。

方案二：使用 JOIN 查询（最推荐）

方案三：批量懒加载（aggressiveLazyLoading + 合理的批次大小）

MyBatis 支持 fetchSize 设置，减少数据库往返次数，但不能从根本上解决 N+1。

权衡原则：

  • 数据量小、关联简单：fetchType="eager" + JOIN
  • 关联数据很少被用到：fetchType="lazy" + 懒加载
  • 大数据量、高并发：避免 ORM 的关联查询，改用应用层手动 JOIN（先查用户，再按 userIds 批量查订单）

Q23. MyBatis 与 Spring 集成的关键组件（SqlSessionTemplate、MapperScannerConfigurer）

SqlSessionTemplate 是 Spring 提供的线程安全的 SqlSession 实现。它通过 Spring 的事务管理和 TransactionSynchronizationManager 来保证：
