AI 应用工程八股文（2）：Prompt、上下文与结构化输出 20 问

总目录：AI 应用工程 160 问

本篇讨论Prompt、上下文与结构化输出。每题先解释概念与原理，再指出适用边界和追问，面向日常学习、方案讨论和通用技术面试。

文中的设计建议与教学示例用于说明方法，不代表某个产品已经实现，也不等于所有厂商接口的共同承诺。协议、API与模型能力涉及版本时，应以明确版本和对应官方资料为准。

核心问答

Q1：Prompt Engineering与Context Engineering有什么区别？

Prompt Engineering强调如何表达指令、示例和输出要求；Context Engineering还要管理检索材料、历史、工具定义、记忆、状态和预算如何进入上下文。二者有重叠，后者不能简单理解为把提示词写得更长。工程目标是提供当前任务需要且可信的信息。

追问：效果下降先改文字，还是检查提供了错误资料？先定位失败阶段。

Q2：系统指令、用户请求、工具结果的角色如何区分？

应用应按平台支持的消息角色和信任边界组织输入。用户表达目标，工具返回证据或执行状态；网页和文档里的文字不应自动变成新的授权。角色有助于组织上下文，但安全还要靠执行层验证，不能仅依赖模型理解层级。

误区：把外部文本拼到高优先级指令中，可能提升其被误当指令的风险。

Q3：好的提示词通常需要哪些部分？

明确任务、必要背景、输入边界、输出结构、判定标准，以及缺少资料或冲突时的行为。优先删除无关内容，加入能区分正确与错误的例子。提示应随任务和模型迭代，并有版本和回归样本，而不是使用统一万能模板。

追问：加“你是专家”能保证专业正确吗？角色描述不能替代资料和验证。

Q4：Zero-shot、Few-shot、In-context Learning有什么区别？

Zero-shot不提供任务示例，Few-shot提供少量示例；In-context Learning描述模型在上下文中利用指令和示例调整表现，不会因此永久修改基础权重。示例要覆盖边界、反例和输出要求，避免只展示非常相似的成功样本。

追问：示例越多越好吗？它会增加成本，也可能引入偏差或挤占关键资料。

Q5：如何写“信息不足时不要编造”？

需要把行为变得可执行：哪些信息属于必需项、何时先澄清、何时给有限结论、如何标出缺失证据。例如明确金额与日期不全时不创建交易，只返回缺少字段。单写一句“禁止幻觉”无法替代数据检查和业务约束。

追问：如何测拒答？加入真实不可回答、资料冲突和答案缺失样本。

Q6：JSON模式与Structured Outputs有什么区别？

只保证或倾向生成合法JSON，与输出满足指定结构是两个层次。结构化输出通常通过受支持的Schema和约束生成提高字段与类型可靠性，但不同厂商和模型支持的Schema子集不同。即使结构正确，字段内容仍可能错误。

误区：合法JSON等于业务合法。应用还要检查权限、范围、枚举语义与关联关系。

Q7：Structured Outputs与Function Calling该怎么选？

要模型直接输出一份可解析报告时，考虑结构化响应；要模型请求外部动作时，考虑工具调用。工具参数也可以受Schema约束，所以两者不是互斥概念。重点是输出被谁消费、是否触发副作用，以及调用结果如何返回模型。

追问：把任意JSON都解释成动作，会失去显式工具边界。

Q8：Strict模式究竟保证什么？

它是某些接口对受支持Schema的约束机制，主要改善结构与参数形状。不能保证模型选对工具、引用真实、数值正确或具有执行权限。还要处理拒绝、截断、连接失败及不支持的Schema；具体条件按目标厂商文档核对。

追问：required、nullable、additionalProperties的要求是否各厂商相同？不是。

Q9：Schema怎样设计才能方便模型填写？

优先明确名称、类型、枚举和单位，减少不必要嵌套和自由文本，清楚说明缺失值如何表示。区分“字段缺失”“明确为空”“无此概念”。Schema不应暴露密钥、私有配置或不必要敏感枚举；业务关系仍需服务端验证。

追问：开始时间必须早于结束时间，这种跨字段约束在哪里检查？执行层。

Q10：为什么约束解码后仍要服务端校验？

约束生成覆盖的是支持的语法和结构范围，不会自动理解真实用户权限、数据库状态和业务规则。解析后应执行类型与范围校验、身份绑定、对象所有权检查、状态前置条件检查，并给出清晰错误。高风险动作不能因模型输出格式正确而跳过授权。

追问：订单ID存在，但属于别人，Schema仍然可能完全合法。

Q11：如何处理输出截断、拒绝和部分JSON？

先检查结束原因与传输是否完整，再决定能否解析。拒绝不应被当普通业务结果；截断可以在预算允许时重新请求，但应防重复副作用。不要从未完成JSON中勉强抽几个字段直接执行写操作。

追问：完整HTTP 200不代表业务完成或结构完整。

Q12：如何管理多轮对话历史？

根据当前任务选择相关历史，保留用户约束、已确认事实、工具结果和未完成状态。可以摘要较旧内容，但关键实体、授权与事务状态最好有结构化存储。避免把所有聊天直接拼接，或删掉决定后续行为的工具返回。

追问：对话消息与业务状态谁更可信？执行结果与服务端状态不能由摘要覆盖。

Q13：对话摘要有什么风险？

摘要可能遗漏否定、时间、条件和信息来源，也可能把猜测写成事实。因此应保留原始记录或引用，区分用户陈述和模型推断，提供可刷新摘要的机制。审批、权限与付款状态不应只存成自然语言摘要。

追问：压缩后如何判断损失可接受？用需要历史约束的回归任务验证。

Q14：长上下文能替代RAG吗？

长窗口可容纳更多资料，但仍要考虑成本、延迟、更新、权限和信息定位。RAG通过选择资料减少输入，长上下文可以承接更丰富的检索结果。哪种更好取决于资料规模、任务形态及评测，不能一概而论。

追问：为什么把全部文档都塞进去，正确率还可能下降？噪声与相关信息利用能力需要测试。

Q15：上下文压缩有哪些方法？

可以去重、过滤、按任务重排、提取相关段落、摘要或将结构化状态移到外部。不同压缩方法损失不同：抽取保留原文却可能漏上下文，摘要更短却可能改写事实。应保留来源与版本，并检查压缩前后任务表现。

误区：压缩Token比例高就说明优化成功。

Q16：如何处理上下文中的冲突资料？

比较来源可信度、生效时间、适用对象和版本，不以出现顺序决定真伪。若规则无法消解冲突，就说明冲突并请求核实。应用可以优先提供有效版本，同时保留审计依据，不让模型凭措辞自信度裁决。

追问：最新文档是否总能覆盖旧文档？仍要看适用范围和变更规则。

Q17：Prompt Caching、响应缓存、语义缓存有什么区别？

Prompt Caching通常复用输入前缀的计算；响应缓存复用历史输出；语义缓存按近似含义查找已有结果。后两者更需要检查权限、时效和问题是否真正等价。输入计算被缓存，不意味着模型以后不需要接收相关上下文。

追问：命中缓存节省多少费用、保留多久？看具体服务文档，不能固定数字。

Q18：如何设计便于缓存的上下文？

在服务支持前缀缓存时，可把稳定说明与工具定义放在前面，将经常变化的请求内容放在后面，保持序列化稳定。优化应通过命中率、延迟和实际费用验证；不要为了缓存而省略关键状态或保留过期权限。

追问：工具列表变化、Schema顺序变化可能影响匹配，需要记录配置版本。

Q19：怎样做Prompt版本管理与A/B测试？

保存模板、示例、模型版本、采样配置和测试集版本。先用同一组保留样本离线比较，再在适当流量中灰度，观察质量、拒答、成本和失败。不要只选改善最明显的几个案例，也不要让Prompt调优反复泄漏测试集。

追问：模型换了但Prompt没改，是否还需要回归？需要，行为仍可能变化。

Q20：多模态输入的上下文需要注意什么？

图片、音频、文档解析结果都有各自的计量与信息损失。OCR可能丢表格、单位或布局，图像中的文字也可能携带不可信指令。处理时说明来源、必要的图文对应关系和质量不足情况，避免把视觉推断写成确定事实。

追问：用户只授权分析某张图片，不表示授权保存或外发所有附件。

以下Schema仅展示字段设计；厂商支持哪些关键字，应以对应文档为准。

模型返回了正确类型的evidenceIds，仍可能引用不存在、无权访问或无法支持答案的文档。应用可以继续检查：ID是否来自本次允许的检索集合、资料版本是否有效、重要主张是否被支持、需要澄清时是否仍擅自给出确定结论。

层次 检查例子
传输 响应是否完整、是否超时
生成状态 是否拒绝或被Token上限截断
结构 字段、类型与允许的键
业务 证据存在、版本有效、答案符合任务
权限 当前用户能够访问对应证据

这些检查各自解决不同问题，不应合并成一句“开strict就好了”。

复习与自检

把每题压缩成30秒定义，再用两分钟说明机制、代价和失败场景。遇到依赖厂商或协议版本的结论，记录适用范围，不背成普遍定律。

  1. 能否与相近概念清楚区分？
  2. 能否给出一个正常流程和一个失败流程？
  3. 能否说明这个方案解决不了什么？
  4. 能否设计一个验证自己判断的实验或测试？
