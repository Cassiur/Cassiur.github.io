文中的设计建议与教学示例用于说明方法，不代表某个产品已经实现，也不等于所有厂商接口的共同承诺。协议、API与模型能力涉及版本时，应以明确版本和对应官方资料为准。

核心问答

Q1：MCP解决什么问题？它与REST API有什么区别？

MCP为AI应用连接外部工具和上下文服务提供统一协议。REST可以承载业务API；MCP则规定工具与上下文能力的发现和交互等机制。服务端仍可能调用REST或数据库。MCP不是模型，也不会替业务接口定义权限和事务规则。

追问：给现有接口加一个/mcp路径，并不自动实现协议兼容。

Q2：Host、Client与Server分别负责什么？

Host是承载AI交互与策略的应用；Client维持与服务端的协议连接；Server暴露工具、资源或提示等能力。一个Host可以管理多个Client连接不同Server。模型一般不直接负责网络连接和令牌存储。

误区：一个MCP Server就是一个独立大模型Agent。

Q3：MCP为什么采用JSON-RPC？请求、响应与通知有什么区别？

JSON-RPC为方法调用、ID关联、结果和错误提供消息结构。请求携带ID并期望响应；通知没有响应ID且不应收到常规响应。HTTP状态、JSON-RPC错误与工具业务错误属于不同层，不能混成同一个成功标志。

追问：工具参数中的业务id与JSON-RPC id不是同一概念。

Q4：初始化与能力协商的流程是什么？

按本文固定的2025-11-25规范，客户端先发送initialize，双方交换协议版本、能力和实现信息；收到响应后客户端发送notifications/initialized，再进入正常运行。后续只能依照已协商能力交互，不能只看SDK方法是否存在。

追问：不支持对方版本或所需能力时，应该兼容降级还是拒绝？要有明确策略。生命周期

Q5：Tools、Resources、Prompts有什么区别？

Tools暴露可调用动作；Resources提供可读取的上下文数据，通常以URI标识；Prompts提供可发现的提示模板及参数。在交互设计中常分别强调模型选择、应用管理和用户选择，但具体呈现由宿主决定，不能据此推导自动执行授权。

追问：资源读取和工具调用都能获取数据，为什么还要区分语义和交互方式？

Q6：tools/list与tools/call怎样工作？

客户端通过tools/list发现工具定义，必要时分页；通过tools/call提交名称与参数，得到内容或结构化结果等返回。服务端可声明列表变化相关能力。工具列表与参数也要考虑当前身份，不应向无权用户泄漏敏感能力。

追问：发现了工具，是否意味着有权调用它？仍要在执行时校验。工具规范

Q7：工具执行错误与协议错误怎样区分？

请求格式、方法或协议处理出错可使用JSON-RPC层错误；工具运行中的业务失败可在工具结果里表达错误状态。这样模型或应用能区分“调用没有成立”和“调用成立但动作失败”。具体SDK封装可能不同，需检查实际消息。

追问：HTTP 200和JSON-RPC result都出现时，工具仍可能报告执行失败。

Q8：Resources与Resource Templates如何使用？

资源用URI定位文本或二进制上下文，服务端可以列出资源，也可以提供参数化资源模板。资源更新通知与订阅取决于能力。应用读取后仍需控制权限、大小、版本与来源；URI本身不是访问授权。

追问：资源URI是否必须是可公开HTTP地址？不必。资源规范

Q9：Prompts与Skill、系统提示有什么区别？

MCP Prompts是协议中可发现、可带参数的提示模板；Skill是目录化任务说明与资源的组织格式；系统提示是模型输入中的指令渠道。它们可以配合，但不属于同一协议对象，不能简单互相改名。

追问：模板从远端返回后，是否就获得高优先级信任？来源与授权仍需判断。Prompts规范

Q10：stdio传输适用于什么场景？

常见本地方式是客户端启动服务端子进程，通过标准输入输出交换JSON-RPC消息。stdout用于协议消息，日志可写stderr，避免污染消息流。进程继承的环境、文件权限和网络能力都需要控制；“本地进程”不等于可信。

追问：服务端打印一行普通日志到stdout，为什么可能破坏协议解析？

Q11：Streamable HTTP和旧HTTP+SSE有什么区别？

本文固定规范定义stdio与Streamable HTTP。Streamable HTTP通过HTTP端点处理消息，可使用JSON响应或SSE承载流，不能简化成“开个EventSource就行”。旧HTTP+SSE传输的兼容由明确迁移策略处理；两者不是完全相同的连接流程。

追问：SSE是传输表现之一，不表示整个MCP就是SSE。传输规范

Q12：HTTP会话、重连与恢复需要注意什么？

会话标识用于协议会话管理，不等于用户身份。连接中断后要依据服务端能力和事件机制决定恢复、重建或查询任务状态。重连不能被当作安全重放所有写调用的理由；业务幂等与协议会话恢复是两层机制。

追问：服务端重启、会话失效与OAuth令牌过期需要不同处理。

Q13：MCP如何进行鉴权？OAuth是否在所有传输里都一样？

HTTP场景的授权规范规定受保护服务如何与OAuth相关机制配合；服务端充当资源服务器并验证令牌用途。stdio常通过运行环境获取凭据，不能照搬浏览器HTTP流程。鉴权证明身份与授权上下文，不自动完成每个业务对象的访问检查。

追问：协议授权与租户内订单权限是两个层次。授权规范

Q14：为什么不能把收到的Token直接透传给任意下游？

令牌通常有特定受众和权限范围。服务端若不验证用途就转发，可能成为混淆代理或扩大权限。连接下游应使用适当授权流程和限定凭据，不把MCP访问令牌当成通用万能钥匙。日志也不应保存原始令牌。

追问：校验签名还不够，issuer、audience、有效期与scope也重要。

Q15：Sampling是什么？为什么需要客户端参与？

它允许服务端通过客户端请求模型生成，而不是要求每个服务端都自行持有模型服务凭据。是否可用取决于能力协商与宿主策略。客户端需要管理用户可见性、模型调用、预算与上下文，不能把服务端请求当作无条件授权。

追问：服务端触发嵌套模型调用时，成本与数据外发由谁控制？Sampling

Q16：Roots是什么？为什么不能把它当沙箱？

Roots向服务端提供客户端相关工作范围的信息，例如工作区根。它帮助协调资源范围，但不能替代操作系统权限、真实路径校验和执行隔离。符号链接、挂载与执行时变化仍可能影响路径边界。

追问：声明“只能访问某目录”，是否意味着进程无法打开其他文件？并不自动保证。Roots

Q17：Elicitation是什么？能直接向用户索要密码吗？

Elicitation允许服务端经客户端请求用户补充信息，具体模式与限制随协议版本变化。表单补充、外部安全交互与工具确认不是同一概念。敏感信息应走规范允许和宿主支持的安全流程，不能随意放进普通表单、模型上下文或日志。

追问：用户拒绝、取消和未提供信息，都应成为明确状态。Elicitation

Q18：进度通知、取消和长任务如何设计？

进度是状态观察，不是完成证明；取消是请求，不保证已经发生的副作用被回滚。支持任务扩展时要按协商能力与对应规范处理，不假定所有客户端都有相同任务接口。长任务仍需要查询、超时、幂等与恢复机制。

追问：客户端断线，后台任务继续还是取消？协议能力与业务政策都要明确。

Q19：MCP服务有哪些典型安全风险？

工具描述与结果可能携带注入，远程地址可能引入SSRF，本地服务进程可能读取过多文件，令牌使用不当会扩大权限。HTTP服务还需按规范检查Origin等要求。应审查来源、约束执行、限制网络与凭据，并记录脱敏审计。

追问：工具注解声称只读，能否无条件相信？不能。安全实践

Q20：怎样证明自己实现了MCP兼容，而不是只做了两个接口？

声明协议版本、传输方式、初始化与能力、支持的方法和错误语义，用真实客户端验证连接、发现、调用、分页及异常。鉴权、取消、资源等未支持的能力要明确。一个教学子集有价值，但不能据此宣称完整兼容全部规范。

追问：SDK升级后新增能力，不代表服务端已经实现并验证。

三层错误对照

层次 示例 诊断方向
传输/HTTP 网络断开、401、不可接受的Origin 连接、认证、代理与请求头
JSON-RPC 消息无法解析、未知方法 消息结构、协议版本与方法支持
工具执行 工具运行后返回isError=true 参数业务语义、外部服务与权限

错误恢复不能仅看HTTP状态。JSON-RPC正常返回result时，工具本身仍可能失败；网络中断也可能发生在业务执行之后。

复习与自检

  3. 能否说明这个方案解决不了什么？
